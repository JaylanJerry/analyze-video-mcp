# 视频 MCP 实测问题修复计划（2026-09-24）

状态：实施中（2026-09-24）。本计划整合 2026-09-24《山姆·奥特曼大战达里奥.mp4》调用、仓库现有 B 批证据和只读代码审查；它不替代 [`todo-v07-proposal.md`](todo-v07-proposal.md)、已接受 ADR 或公开 API 契约。

## 目标与边界

- 先让现有 `analyze_video(video, question?)` 稳定提供可追溯的抽样画面和声音结论，再考虑 v0.7 的新 Tool。工具名、输入字段、默认模型和本地上限保持现状。
- 保留可用的部分结果，但用户明确要求声音而模型未确认听到时，结果必须清楚说明该部分未完成。`audio_analyzed=true` 只表示含音轨的视频已提交，不得解释成模型听清。
- 成功与错误输出都不能回显凭证、本地绝对路径或内部 `oss://` 地址。模型生成的正文和观察条目同样是不可信输入。
- 不增加生产依赖，不自动转码，不恢复上游五 Tool 接口，不推送、打 tag 或发布。新 Tool、公开字段、默认值或外部运行时如需改变，先更新规格与 ADR 供用户审阅。
- 用户已授权本轮必要的付费 live 测试；优先使用 mocked 测试和公开夹具。不得在文档、fixture、命令参数或输出中放入密钥及私人媒体内容。

## 当前证据

1. 本次约 62.902 秒源文件经只读 FFprobe 确认为 H.264 视频与 44.1 kHz 双声道 AAC；FFmpeg `volumedetect` 为 mean −14.3 dB、max 0.0 dB。电平只能证明有非零信号，不能判定声音语义。MCP 返回 `audio_analyzed=true`、`audio_observed=false`，音频条目仅为 `uncertain`，同时 `ok=true`。工具没有把不确定内容冒充 `heard`，但整次成功状态不能表达音频部分未完成。
2. [`PROVIDER_PROTOCOL.md`](../../../docs/PROVIDER_PROTOCOL.md) 第 1e 节已有受控对照：默认 `qwen3.8-omni-flash` 能识别替换的清晰语音，却漏报用户确认存在的背景歌曲；`qwen3.5-omni-plus` 对歌曲存在的报告符合该次用户真值。尚不能推断所有歌声或音效条目准确，也不能单凭这些样本定位根因。
3. 无付费 `dist` 探针：报告正文写“明确听到电子乐”，音频观察只有 `uncertain`，`parseEvidence` 仍给 `violations=[]`；`99:99` 时间码在 62 秒媒体上也能通过。模型若在成功正文或观察里回显测试用 `oss://` 地址，文本和 `structuredContent` 都会保留它。这些是实现缺口，不依赖模型真实犯错。
4. `src/sse.ts` 接受 `finish_reason=length` 作为完成，`src/bailian.ts` 没有把 `finishReason` 和已解析的 usage 传给最终结果。证据纠错可能再次分析整段视频，耗时与计费缺少最终可见诊断。
5. 本机 Codex 配置的 MCP `args` 指向已不存在的旧 `dist/index.js`；当前仓库 `dist/index.js` 存在。本次会话未直接挂载该 Tool，改由持久 stdio 客户端调用当前构建。首次临时客户端的 `v3Schema.safeParse` 错误是调用方误传结果 schema，并非服务端缺陷；修正后 MCP 调用成功。
6. 审查基线：`npm test` 263 通过、6 跳过；typecheck、lint、format:check 通过。当前分支 `codex/optimization-prep` 比 `origin/main` 领先 3 个提交，工作树在写本计划前干净；这些提交尚不等同于已发布版本。

## 修复顺序

### F0. 恢复 Codex 安装入口（本机配置；独立于代码修复）

**状态（2026-09-24）：已完成安装、命令行和新会话 Tool 调用验收。** Luna 修复与本轮补丁已合入主仓库；旧全局包已卸载，独立 tarball 已安装而非源码链接。诊断卡顿的根因是 Windows 用户环境变量回退对五个字段多次启动 PowerShell；现改为一次批量读取并短时复用，全局安装版 `--doctor --json` 在约两秒内返回 `ok=true` 且注册了唯一 Tool。Codex 配置已指向全局安装的 `dist/index.js`，全局包真实 stdio 握手通过。用户重启后，新会话已在 Tool 列表发现并成功调用 `analyze_video` 分析原片。

**问题：** 配置目标文件不存在，导致用户不能稳定从 Codex Tool 列表调用当前构建。`QWEN_ALLOW_ANY_LOCAL_VIDEO=on` 是 ADR 0021 接受的安装级选择，默认发布行为仍须为 `off`。

**工作：** 核对当前安装命令和构建目标，只调整必要的命令/路径；不读取或输出配置中的密钥。重启或新建宿主会话后验证 `initialize`、恰好一个 `analyze_video` Tool，以及公开 3 秒夹具的 GUI 调用。工作树路径不应被误当成长期稳定安装路径。

**验收：** 新会话可直接调用 Tool；`--doctor --json` 给出安全的配置来源与本地路径策略；不依赖临时手写客户端。若外部配置修改受权限审查阻止，完成其它修复并明确记录阻断原因。

### F1. 封住成功结果的敏感信息出口（必须先做）

**状态（2026-09-24）：已实现并通过 mock。** `sanitizeEvidenceReport` 与 `sanitizeProseAnswer` 在成功出口统一清理正文、观察、推断、不确定项；canary 覆盖 `oss://`、凭证形态、含空格 Windows 路径，同时保留普通 HTTPS 链接。无 GUI/live MCP 出口验证。

**问题：** 当前只对错误详情做脱敏；模型生成的成功 `answer`、观察、推断与不确定项可把内部地址回显给 Agent。

**工作：** 在单一成功结果出口处理文本与结构化条目，保留正常的媒体描述。覆盖 `oss://`、凭证形态和本地绝对路径；避免把真正的普通字幕或 URL 错删。不能仅过滤文本而留下 `structuredContent`。

**验收：** 用虚构 canary 分别注入正文、每类观察和散文兜底，Agent 可见文本与结构化结果均不含敏感原值；既有错误脱敏测试继续通过。优先改 `src/evidence.ts`、`src/server.ts` 及相关测试。

### F2. 加强证据与时间码门槛（必须先做）

**状态（2026-09-24）：已实现并通过 mock，散文证据门仍有限。** 正文确定性声音结论与 `heard` 条目做保守词句对齐；不支持时清除对应确定性句并提示未确认，不为仅有此类问题再次计费。否定句“没有听到”不会误判为声音确证。`MM:SS` 格式、秒范围、同模态时间顺序和已知本地时长边界已覆盖。散文回答仍是无结构证据回答，不能据此视为“已核实”；词句对齐也不能证明观察真实。

**问题：** 分项为 `uncertain` 时正文仍可写确定的听音结论；普通散文可绕开分项证据；任意非空时间码可通过。模型 `confidence` 是自报值，不是准确率测量。

**工作：** 对声画确定性结论建立正文与分项的一致性约束。无法可靠解析的散文只作为无结构证据的回答，不得产生“已核实”语义。验证 `MM:SS` 格式、正序和已知媒体时长边界；越界或乱序的条目降级或拒绝，不能作为直接观察输出。保留抽样时间码的不精确性提示。

**验收：** 上述三个无付费反例都不再作为无违规完整报告交付；正常的公开夹具声画观察不被误杀；文本与 `coverage` 不互相矛盾。优先改 `src/evidence.ts`、`src/server.ts`、`test/evidence.test.ts`、`test/tools.test.ts`。

### F3. 正确识别截断、记录用量与重试（F1/F2 后）

**状态（2026-09-24）：已实现并通过 mock。** `finish_reason=length` 现在返回 `PROVIDER_RESPONSE_INVALID`，不交付部分答案；安全诊断可记录事件数和 token usage。成功调用会记录请求数、纠错次数、总耗时、request id、结束原因与跨纠错调用汇总的用量。provider 错误仍没有写入 Agent 可见结构字段，限本地 stderr 诊断。

**问题：** `finish_reason=length` 当前仍被当作完成；SSE 已解析 usage，但最终分析结果丢弃它。纠错重试可能重新计费一整段视频。

**工作：** 将 `finishReason`、usage、纠错次数和阶段耗时保留在内部诊断中；截断必须返回明确的不完整结论或安全错误，不能以可截出的 `answer` 冒充完整结果。对重复付费分析制定上限与可见诊断，不记录原始响应或私人内容。

**验收：** mocked SSE 覆盖 `stop`、`length`、无正文、纠错二次调用；诊断能解释一次调用产生的模型请求数与用量是否可得。若需增加公开字段，先提交 API 契约和 ADR 供审阅。优先改 `src/sse.ts`、`src/bailian.ts`、`src/server.ts` 与测试。

### F4. 声音部分完成语义与模型对照（F1/F2 稳定后）

**状态（2026-09-24）：已证实模型差异；本机选用可撤销的模型覆盖。** 已在主文本对 `audio_track_present=true && audio_observed=false` 时提示“没有确认声音，不等于静音”。公开 3 秒夹具在默认 `qwen3.8-omni-flash` 上同时命中声画预设数字；用户重启后的 Codex 会话调用完整原片时，默认模型仍给 `audio_observed=false`，三个音频条目全为 `uncertain`，未识别用户确认的背景歌曲。同一完整原片经安装包设置 `QWEN_MODEL=qwen3.5-omni-plus` 后给出 `audio_observed=true`，六条 `heard`，其中背景音乐判断吻合用户真值。20–30 秒原音配黑画面的 10.08 秒对照仍报告音乐，排除“只凭原画面动作猜有音乐”作为该对照的解释；但全片和短片对人声演唱的判断不一致，动作音效亦未独立核听。用户已确认只修改这台 Codex 安装的 `QWEN_MODEL`，公开默认值与 Tool schema 均不变；此后重启的新会话已确认加载配置。

**问题：** 现有覆盖字段已正确把本次 `audio_observed` 标为 `false`，但明确询问声音时仍无法在主结果中清楚区分“调用成功”和“音频内容分析完成”。根因尚未定位。

**工作：** 先用现有字段和用户可见文本给出明确的部分完成说明；设计机器可读 `incomplete` 状态时遵守公开契约审阅流程。用相同问题对公开语音夹具、已知音乐片段、无音轨/静音夹具和本次来源的短片做对照；分别记录请求层、报告层、用户真值与本地测量，不把音频电平当作歌曲证据。比较当前默认模型与已验证可选模型后再决定模型策略或 v0.7 独立音频路径，不为单个素材硬编码结论。

**验收：** 音频未确认时，用户无需查看 `structuredContent` 也能理解结果仅覆盖画面；有可靠 `heard` 的控制样本不被全局降级；测试报告能区分模型漏报、上传失败和证据门槛拒绝。付费 live 仅在本地 mocked 回归通过后运行，优先短片和已有上传缓存；记录调用次数、模型、耗时、request id、覆盖信号和结论，不保存私密媒体或原始全文。

### F5. 媒体事实措辞与探测失败（F1–F4 后）

**状态（2026-09-24）：已实现并通过 mock，真实容器覆盖仍有限。** 轨道探测完整且没有该轨道时才给 `false`；缺少或不可读 `moov` / `trak` / 必需结构时为未知，公开覆盖字段省略，不再当成无轨。轻量 fourcc 探测不能证明整条轨道可解码。已覆盖有轨、视频独轨、无可读轨道和无 `moov` 的测试；其它损坏容器变体未穷尽。

**问题：** `stsd` fourcc 探测无法证明整条音轨可解码；读不到轨道与确实无轨道都可能得到空数组，当前文案却可能写成“本地已确认的可解码音轨”。

**工作：** 区分已发现受支持编码、探测未知、确实无轨道三种状态；调整文案和覆盖字段的解释。是否改变未知结构的放行策略先与现有“未知时长允许”的契约分开审阅。

**验收：** 有轨、无轨、损坏/不可读 `moov`、不支持 fourcc 的夹具得到不互相矛盾的结果；不把轻量探测写成完整解码验证。优先改 `src/media.ts`、`src/evidence.ts`、`test/media.test.ts`。

## 重启后复测与下一轮计划（2026-09-24）

用户重启后的 Codex 直接调用确认 `model=qwen3.5-omni-plus`、`audio_track_present=true`、`audio_analyzed=true`、`audio_observed=true`。完整约 62 秒原片的模型报告含从开头持续到结尾的背景音乐，且未报告清晰人物对话；背景歌存在这一点符合用户提供的真值。模型同时把歌声写成「中文女声」，并对若干画面细节给出 `confidence=1`，但这些细节未独立核验。`audio_observed=true` 只证明通过了现有结构化证据门，不证明每条声音细节准确。

本次文本还出现「正文中缺少对应证据的声音结论已移除」及同义的 `uncertainties` 条目。代码位置是 `src/evidence.ts` 的 `removeUnsupportedAudioClauses` / `sanitizeEvidenceReport`：规则在移除部分正文时，把内部纠错说明放进最终面向用户的报告。该说明本身不含秘密，但让结果读起来像调试信息，而且被删除的具体声音结论无法从最终结果复核。以下工作只继续修既有 `analyze_video`；不以这次单片成功为由修改公开默认模型或开启 v0.7 新 Tool。

### N1. 整理证据纠错后的用户可见结果（已完成，2026-09-25）

- 先用本次输出形状建立无付费回归：正文包含未获 `heard` 支持的声音细节，同时音频观察含已确认背景音乐；覆盖纯否定句和只有 `uncertain` 的情况。

### 后续规格审议：静音音轨上的 `heard` 误报（研究已完成，未接入生产）

- 问题分层：MP4/AAC track probe 只说明容器里有轨道；解码器完整成功且产出正样本才证明可解码信号；只有全轨 PCM 样本恰为零才能确认数字静音。模型的 `heard` 是独立模型报告，音乐、歌曲、歌声、对白及音效是语义层判断。非零电平本身不能证明可听、音乐或歌曲；和弦音调夹具不是歌曲/歌声真值。
- 建议最小路径：仅供 v0.7 `analyze_audio` / `audit_media` 使用用户自行安装的 FFmpeg/ffprobe；固定参数、`shell:false`、无网络下载、解码到 null、保留样本数及峰值/RMS，不生成 WAV；逐条音轨成功后才能判定文件级数字静音。失败、缺工具/轨道、空样本、部分解码、超时、取消或输出上限均回 `unknown` + `incomplete`。若模型报 `heard` 而本地测量确认全零，保留两类证据并把该语义 finding 降为 uncertain；非零信号不替模型作语义裁决。
- 授权输入路线实验：`scripts/research/file-handle-audio-input.mjs` 在 3 个固定合成样本上比较原路径、`pipe:0`、继承 FileHandle fd + `fd:`、权限模式临时副本。Windows Node 24 + FFmpeg 8.1.1 下，3 种授权 handle 路线全解码完整，包括 moov 位于 EOF 的 mp4/mov。推荐 Node 继承已授权 read-only FileHandle fd 为 child stdin，FFmpeg 用 `fd:` 与 protocol whitelist；无路径重开、无需全片复制、支持随机访问。多轮小样本耗时范围：fd 46–69ms、原路径 60–100ms、pipe 61–85ms、临时副本+解码 60–106ms；临时副本占用正好输入大小。父进程 RSS 差是噪声值，未测 FFmpeg 子进程峰值 RSS。固定 100ms 取消实验中三种 handle 输入路线均回收子进程，临时文件在进程关闭后可删。Node Windows `0o600` 并非已验证私有 ACL；故临时副本不作为默认方案。继承 fd 只消除按路径替换，不阻止同一文件并发原地修改，也无法单靠 Node 限制 FFmpeg 读取到授权时字节长度；维护者若要求不可变快照或硬 byte cap，需另审私有副本 ACL 或 OS snapshot/lock。
- 实施边界与验收清单：仅支持受测到的平台/容器版本，不支持时 fail closed 为 `unknown`/`incomplete`；子进程最小环境不得继承 `DASHSCOPE_API_KEY`，固定 executable/参数、`shell:false`、`fd:` protocol whitelist、输出/耗时/并发上限；启动前 fstat 并拒绝超过本地输入上限，结束后复查打开 handle 的 identity/size/mtime，变化则 incomplete。需明说继承 regular-file fd 本身不提供硬 byte-range cap，元数据复查也不构成不可变快照；若维护者要求硬边界或抵御同一文件并发修改，则要先审议有 Windows user-only ACL 的快照副本/OS lock，不能假称当前 fd 方案已满足。FFmpeg 完整退出、每轨样本统计有效，取消时终止并 await close；验证 source handle 在测量后仍可从 offset 0 上传；不要按原路径重开，不默认复制。跨平台门槛：Windows Node 22/24、Linux/macOS Node 22/24，MP4/MOV faststart 与 tail-moov、长音轨/大体积数据、多轨、坏截断尾、超时/取消、磁盘/输出限制；长媒体测量父进程和子进程峰值 RSS。
- 研究原型：`scripts/research/audio-signal-probe.mjs` 只枚举固定仓库夹具，不接受用户路径、不联网、不写音频文件。测得两段合成 AAC 静音为 complete 且 peak/RMS `-inf`；合成三音和弦及 `live-av.mp4` 为非零。此证据验证信号层可区分性，不验证听感语义或生产安全路径。
- 决策状态：ADR 0019 仍为 Proposed。此阶段没有改生产音频路径、公开 Tool schema、默认模型或依赖；没有新增 live 调用。实施前需由维护者审阅是否接受外部运行时、超时/并发上限和输入身份解决方式，并按跨平台真值集扩展验收。
- 现有工具边界：该提案只使新 v0.7 Tool 能识别数字静音与模型 `heard` 的冲突，不会自动修复现有 `analyze_video` 的静音误报。若用户也要求旧 Tool 使用这项测量，需另审兼容性、运行时缺失时行为和报告覆盖规则。

**状态：** N1 已修并通过回归；N2 已完成小型探索性对照，暴露 qwen3.5 在静音音轨上的 `heard` 误报，不足以做整体模型排序；N3 包安装和新 stdio 握手通过，桌面新会话原片调用因避免重复付费未做。v0.7 的 `analyze_audio`、确定性音频测量和 `audit_media` 仍需独立规格/ADR 审议。
